# Contrato para asignar roles personalizados locales

Este documento concreta la parte pendiente de `P2-02`. La migración `0030_custom_panel_roles.sql` y la API/web ya admiten asignar roles personalizados en `algym_test`. La migración aún no se aplicó a `algym` operativa: falta respaldarla y terminar las pruebas de aceptación. Un rol personalizado se representa con el valor exclusivo `custom` del enum y su `panel_role_id`; nunca como `employee`, porque las políticas SQL heredadas consultan directamente el enum y podrían conceder acceso de empleado sin el permiso correspondiente.

## Modelo y fronteras de autorización

1. Agregar un valor distinto `custom` al enum y una referencia opcional desde `profiles` a `roles.id`. Para `role=custom`, la referencia es obligatoria y debe apuntar a un rol existente con `scope=panel` que no sea de sistema. Para los roles de sistema y los clientes, la referencia debe estar vacía. La base debe imponer estas invariantes, además de validarlas en la API.
2. El rol efectivo de autenticación es el `slug` de la referencia para `custom` y el valor del enum para los demás. `get_current_role_slug`, `get_profile_role`, `get_current_permissions`, `private.current_actor_has_permission` y la visibilidad del catálogo RBAC deben usar esa regla. `is_owner` y `check_is_admin` conservan el privilegio exclusivo de sus valores explícitos del enum.
3. Auditar cada política y función SQL que compara `get_my_role()` o `profiles.role` con un rol del sistema. Un rol `custom` no debe heredar acceso de `employee`, `trainer` o `admin`; donde un permiso específico deba conceder acceso, la política debe usar `has_permission` y la fila de destino pertinente. Las funciones de Caja que reciben un `slug` deben seguir comprobando `auth.uid()` y el permiso concreto.
4. La API `/users` acepta un `slug` de `scope=panel` existente. Crea o cambia el perfil y la referencia de rol en una transacción, revoca las sesiones al cambiar de rol y preserva la protección del último owner. Asignar `owner`/`admin` y un rol personalizado queda reservado a owner/admin mientras se valida la matriz completa. El listado devuelve el `slug` efectivo y `/users/roles` incluye los roles personalizados asignables.
5. `/roles` cuenta usuarios por rol efectivo. Al borrar un rol asignado exige un reemplazo válido del mismo `scope`, reasigna dentro de la misma transacción, revoca las sesiones afectadas y luego borra el rol. El reemplazo puede ser otro rol personalizado o uno de sistema permitido por la autorización del actor.
6. La web obtiene las opciones desde `/users/roles` y muestra a los usuarios con rol personalizado en la tabla. El backend valida el `slug` elegido contra los roles de panel existentes. La autenticación y el redireccionamiento usan `authorization.scope` y permisos de la API, no una lista fija de cuatro slugs.

## Pruebas obligatorias antes de aplicar la migración a `algym`

- En `algym_test`: crear un rol personalizado sin permisos y un usuario con ese rol; comprobar login de panel y rechazo de clientes, caja, pagos, inventario, roles y usuarios.
- Conceder un permiso a la vez y comprobar que abre solo su operación prevista, incluyendo RLS, no solo botones de la web.
- Cambiar rol y permisos mientras hay sesiones activas; verificar revocación y nuevos permisos tras login.
- Rechazar referencia a rol de cliente, rol de sistema como `custom`, rol inexistente y asignación de owner/admin por actor no autorizado.
- Borrar un rol asignado sin reemplazo debe fallar; con reemplazo debe conservar usuario e historial y revocar la sesión. Probar la protección del último owner.
- Pasar suite completa del backend, typecheck/build y pruebas web; hacer respaldo verificado de `algym` antes de aplicar la migración. Después, probar la interfaz autenticada con red externa bloqueada.

El código pasó 145/145 pruebas del backend desde `algym_test` recién creada, TypeScript y build de la web. La prueba de rol sin permisos verificó acceso denegado en clientes, caja, pagos, inventario, roles y usuarios; `customers.view` abrió solo clientes, y con una selección de permisos de lectura se abrieron 11 rutas representativas. Los cambios de permisos revocaron sesiones. Con `exercises.create`, `products.create`, `inventory.adjust`, `customers.create` y `routines.view` concedidos de forma separada, la API y RLS permitieron crear un ejercicio, producto, ajuste de stock, cliente y plantilla; se rechazaron las demás escrituras y se pudieron leer los registros creados. La prueba detectó políticas antiguas de inventario y perfiles de clientes basadas en slugs fijos; `0030` agrega políticas por permiso para roles personalizados. También se verificó rechazo de rol de cliente, rechazo SQL de un rol de sistema como referencia `custom`, reasignación de usuarios activos y eliminados a otro rol personalizado y luego a empleado al borrar los roles, y protección del último owner. La matriz descubrió que el perfil de usuarios internos podía tener `birth_date` nula; el contrato backend/web ahora la admite y permite editarla. Sigue pendiente probar las demás escrituras por módulo, la interfaz autenticada, el respaldo de `algym` antes de aplicar `0030` y la operación sin red externa. `P2-02` permanece abierto hasta completar esas puertas.
